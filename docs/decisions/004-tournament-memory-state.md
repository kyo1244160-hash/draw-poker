# ADR-004: トーナメント状態はメモリで管理する

- **日付**: 2024-04（トーナメント機能実装時）
- **ステータス**: 採用

## コンテキスト

トーナメントの進行中状態（現在のブラインドレベル・テーブル一覧・脱落順序・レイトレジスト開放フラグ）をどこで管理するか。DBに毎回書き込む方法と、メモリで管理する方法がある。

## 決定

進行中トーナメントの状態は `tournamentManager.js` の `tournaments: Map<id, Tournament>` でメモリ管理する。DB には `status` の変更と最終結果のみ書き込む。

## 理由

- ゲームのアクション（ベット・ドロー）は秒単位で発生し、毎回 DB を読み書きするとレイテンシが問題になる
- ブラインドレベルタイマーや脱落検知はメモリ上で管理する方がシンプル
- Render.com の無料プランはシングルインスタンスのため、メモリ共有の問題がない

## 結果

**利点**:
- 高速（DB アクセスなしでゲーム状態を参照できる）
- ロジックがシンプル

**欠点・リスク**:
- **サーバー再起動でメモリが失われる**: 進行中トーナメントが失われる。Render はデプロイのたびに再起動するため、デプロイ中はトーナメントを開催しないこと
- `isEliminated` の確認など、一部の処理でメモリが取れない場合の fallback（DB の `tournament_results` の存在確認）が必要
- 複数インスタンスへのスケールアウトが困難（Redis 等での状態共有が必要になる）

## フォールバック設計

`/api/tournament/[id]/entry` の `isEliminated` チェックは以下の順で判定する:
1. `tournamentManager.getTournament()` → `eliminationOrder` を確認（メモリ）
2. 取得できない場合: `myEntry`（`tournament_results`）が存在すれば脱落済みとみなす（DB）
